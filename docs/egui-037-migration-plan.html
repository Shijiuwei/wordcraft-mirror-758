1. What is and is not changing

WordCraft already uses the 0.36 App::logic / App::ui split and an existing root Ui. App::logic is already called before every UI pass, including repeated passes; App::ui already receives the root Ui. The 0.37 migration must preserve that architecture rather than rewriting it. The real work is:

  1. making the dependency graph coherent and immutable;
  2. repairing the concrete 0.37 API breaks;
  3. removing application-side text processing that the fork now performs correctly;
  4. preserving one-shot lifecycle work across repeated passes and logic-only frames;
  5. validating that the page, chrome, accessibility, input, clipboard and save/reopen behavior remain what users expect.

No engine, command id, document format, undo semantic or persistence format is intentionally changed by this migration. The app remains Session-driven; egui remains a thin L6 front end.

Required design. WordCraft is one of the eleven craft-ui capture consumers and adopts the shared helper only after CL-2F freezes it; it does not take the provisional CL-2 revision used by the DesignCraft/GridCraft pilots. The callback contract is:

  • Keep request admission, paths, reply schema, settling delay and the 8 s deadline in WordApp. Each request record owns a strong completion slot and waker; the ScreenshotCallback holds only a Weak reference to the slot and receives pixels only. It must not capture WordApp, a Context, a file path, or an unbounded mpsc::Sender. The callback stores the image, validates it, releases the lock, and only then invokes the live slot's app-owned waker. It never calls Context::request_repaint itself and never wakes while holding the lock; never strongly capture a context from a callback queued in that same context.
  • Context::request_screenshot itself schedules a repaint: it calls send_viewport_cmd -> send_viewport_cmd_to -> request_repaint_of. Only callback arrival is documented not to request a repaint. Do not claim the request is repaint-free; keep the existing request_repaint_after(16 ms) while a request is pending and wake explicitly after completion.
  • Admit by count and bytes. Before issuing, estimate width * height * 4 from the current viewport logical content and pixels-per-point with checked arithmetic, then reserve its working set (raw RGBA + worst-case PNG + base64, a 10/3 factor) in an in-flight budget that also counts completed-but-undrained slots. Use the shared defaults: at most 4 outstanding requests, 128 MiB reserved per image and 256 MiB aggregate; reject excess admission without evicting earlier requests. A 4K viewport at 2x is about 7680x4320x4 ~= 127 MiB raw and is therefore rejected by the working-set limit rather than silently exceeding the encode peak. Revalidate the checked dimensions and geometry epoch immediately before issuance.
  • Bind the image to the issuance-time UI geometry: logical content/screen bounds, size, pixels-per-point, zoom and surface epoch. On completion, validate dimensions/byte length against the reservation and that epoch. Any geometry/DPI/zoom change before save, even a change back, cancels and retries within the deadline or returns an explicit stale-capture error; never combine old pixels with current geometry. With an unchanged epoch, derive the pixel scale from the returned image dimensions and verify aspect/rounding.
  • collect_screenshots drains the slots unconditionally in logic, matches the request record, calls control::save_screenshot(&image, path.as_deref()), sends exactly one reply, and releases the slot and reservation. A timeout/cancel/drop removes the record and releases the slot; a late callback then finds a dead weak reference and retains nothing, writes no file and sends no second reply. Retained image bytes must return to zero after drain, timeout, cancel and shutdown.
  • Hidden windows: the screenshot command itself forces a full hidden App::logic + App::ui pass (ActionRequested::wants_paint()), while callback arrival does not repaint. A request queued in logic but issued only in ui, including every remaining settling frame, must therefore send ViewportCommand::RequestPaintWhileHidden from the logic side to reach issuance; a wake/repaint alone may run hidden logic only. Keep the timeout contract and test both the forced pass and the queued-not-issued settling path.
  • The app has one root viewport. If child viewports are added later, route requests by ViewportId and generation; do not reuse an old token for a new document or viewport.
  • ui_shot uses Harness::render, not the viewport callback; keep it as a separate headless path. Do not make ui.render depend on the native callback.
  • The suite has fourteen capture consumers. The eleven existing craft-ui consumers require CL-1 and CL-2F; only the DesignCraft/GridCraft pilots use the reviewed CL-2 provisional revision, and their adapters are reviewed before CL-2F freezes the API. DeckCraft, FigCraft and ArtCraft Native keep contract-compatible local adapters; ai-egui has no capture path. Do not add craft-ui solely for capture; if DeckCraft/FigCraft later adopt it, WordCraft's adapter stays unchanged.

Tests: four-request/128 MiB/256 MiB admission, two outstanding requests with distinct tokens, out-of-order completion, callback once and no self-wake, late callback after timeout/cancel (no file/second reply), forced hidden pass, queued-not-issued RequestPaintWhileHidden, resize/DPI/zoom change and change-back, and retained-bytes-zero after drain/shutdown.

5. Lifecycle, root Ui, hidden windows and repeated passes

5.1 What eframe does

In 0.37, eframe calls App::logic and App::ui inside Context::run_ui for every pass on native and web (crates/eframe/src/native/epi_integration.rs:349-365 and crates/eframe/src/web/app_runner.rs in the target source). Context::run_ui may run the closure more than once when a pass calls request_discard (default max_passes = 2). new_input.take() gives events/dropped files to the first pass only. A hidden window normally goes through update_logic_only -> Context::run_logic, which updates only viewport/focus state and leaves events/time/layout from the previous UI pass. However a pending ViewportCommand::Screenshot or RequestPaintWhileHidden makes eframe run a full hidden pass (is_visible = viewport.info.visible().unwrap_or(true) || actions_requested.any(ActionRequested::wants_paint)), so ViewportInfo::visible() is not a phase indicator. After a normally completed run_ui, current_pass_index() is zero (end_pass takes the output); do not use a stale nonzero index as evidence of hidden work. This is the exact contract the WordCraft code must be audited against.

5.2 logic is currently mostly idempotent; fix the exceptions

WordApp::logic (lib.rs:2087-2238) drains channels (drain_control, zotero::poll, read_aloud::poll, poll_file_dialog, drain_inbox, drain_pasted), ticks recovery/autosave, issues/collects screenshots, and handles dropped files. Most drains are inherently once-only because they take/recv. The audit must prove, not assume:

  • Dropped files are stale in hidden/forced logic passes. lib.rs:2208-2230 reads ctx.input(|i| i.raw.dropped_files.clone()) without taking. A hidden run_logic frame or a forced hidden full pass can see the last shown frame's drops and open/insert them again. The browser shell already takes the vector in apps/wordcraft-web/src/web.rs:119; native WordApp::logic still clones it. Change WordApp::logic to ctx.input_mut(|i| std::mem::take(&mut i.raw.dropped_files)) and handle the drained vector. Apply the same rule to any future input-derived queue read in logic; never poll a prior pass's event twice.
  • SmartArt Tab uses ctx.input_mut(|i| i.consume_key(...)) (lib.rs:2106-2118); consuming makes a repeated logic pass harmless. Keep that pattern.
  • Synthetic input (raw_input_hook, lib.rs:2325) runs before each frame, not once per UI pass, and can run on a hidden update_logic_only tick. Keep at most one unapplied synthetic gesture step pending until a full WordApp::ui pass consumes it; repeated hidden logic ticks must not inject the next step, and a press/release pair stays two ordered events, never collapsed. When queued synthetic input needs a UI pass while hidden, request paint through the same RequestPaintWhileHidden path as 4.4.
  • Screenshots replace event collection with the request-owned completion slots in 4.4; a repeated pass must not issue the same request twice. queued_shots and the request records (with their slots/deadlines) remain the one-shot state.
  • Autosave sets last_autosave before running file.save (lib.rs:2312-2325); a second logic pass in the same frame sees the new timestamp. Keep that ordering; add a test with a forced double pass that counts save calls.
  • Recovery/read-aloud/Zotero mutate state flags (recovery_seen, read_aloud_at, zotero channel state). Add a forced double-pass test that asserts one recovery tick, one status transition and one Zotero answer per event.
  • report_dirty is idempotent; do not move it out of logic/ui.
  • Undo transactions are engine-owned. Do not open/close a transaction in logic on every pass; only commands do. A repeated pass must not add an undo step. The IME delete+commit path explicitly joins the typing group once.

6.4 IME, bidi and graphemes

  • Preedit/commit/cancel: one edit and one undo step; candidate window rect follows the caret.
  • DeleteSurroundingBytes: exact byte replacement on macOS/Wayland; char-count path remains for web; both refuse non-boundary ranges without panicking; deletion-only and empty-commit batches work. Inside an equation a byte range has no reliable tree mapping: the request is refused, the composition interrupted and only the replacement immediately paired with the rejected deletion dropped — the next Commit, or an adjacent Text + Commit pair. Any later text/commit in the same raw-input batch is fresh input and must apply, as is a later direct commit without a pre-edit (no persistent tombstone). An over-cap equation deletion likewise clears the painted pre-edit and any earlier deletion's replacement join before it interrupts. The backend's composition interrupt fences protocol-late stale input; an untagged synthetic event in a later frame cannot be distinguished from fresh input. These are synthetic contract tests; native macOS/Wayland IME traces are separate.
  • E21b outgoing surrounding text: after delete+commit and deletion-only batches, after focus/password transitions and with two windows, the payload carries the logical committed text and byte cursor/anchor with preedit excluded. A kittest event test is not native IME evidence.
  • Bidi: Arabic/Hebrew comment balloon reads from the right, a Latin word inside an Arabic paragraph keeps its left-to-right order, brackets mirror correctly, and no double reversal occurs in Backstage file names. Test screen x positions of first/last words, not just string equality.
