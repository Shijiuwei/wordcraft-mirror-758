Drawing payloads

DOCX textboxes retain their own frame and story when they contain an inline picture. The direct WPS payload takes precedence over picture blips inside its text. Textbox fitting and floating-child paint require separate qualification. A shape's own picture fill retains its existing image fallback.

Comment command update: 2026-10-14 · malformed explicit IDs rejected; synthetic refusal, undo/redo and DOCX save/reopen checks (#1690 finding 3). Readiness estimates unchanged.

Comment commands reject explicit negative, floating-point and wrong-type IDs before editing or using the caret. Valid Delete, Resolve, Reply and Edit operations, including omitted caret IDs for Delete/Resolve, have undo/redo and two synthetic DOCX save/reopen checks preserving body and comment data (crates/engine/tests/it/comment_ids.rs). This does not extend the modern-comment format coverage listed below.

Legacy DOC/DOT document properties

The binary Word reader imports SummaryInformation text properties: title, subject, author, keywords, description, last editor and revision. Code-page strings use their declared Windows single-byte encoding, UTF-8 or UTF-16LE; UnicodeString lengths are counted in UTF-16 units. Metadata streams are capped at 2 MiB and individual values at 64 KiB. Invalid optional metadata is skipped without losing the document body. Creation/modification timestamps and DocumentSummaryInformation/custom properties are not imported by this change; DOC/DOT remain read-only formats and encrypted legacy documents remain unsupported.

Tests create OLE property sets in Rust and exercise the public document reader for normal DOCs, templates, accented/Cyrillic/Unicode properties and malformed lengths/offsets. A local LibreOffice-generated DOC and DOT containing an original synthetic document reproduced the missing-title bug before this change and retain their title after it.

Custom XML store preservation

A reduced original bound-control DOCX loses its backing data, item properties and relationship on main, both without editing and after unrelated edits. Main's content-control support (#381) preserves control metadata, including binding attributes, while this custom XML path keeps the backing store through the bounded opaque part graph: payload bytes, content types and related-part IDs survive two edited save/reopen cycles. The public dataBinding contract maps a control to a custom XML data part; its item properties identify the store. Keeping displayed text alone does not preserve that mapping. This change preserves stores without evaluating XPath or synchronizing control edits into XML. Focused original tests cover package/main roots, multiple/shared stores, cycles, external schema references, missing parts, UTF-16 payloads, strict relationship types and reserved filenames. The bibliography names used by #532 are reserved; bibliography already loaded into the source model belongs to its writer. Word-derived files are not fixtures. No readiness estimate rises from these synthetic package checks, and native Word rendering/binding behavior remains untested.

Native save-path guarantees

Native io::save_path_with serializes (and, for password-protected DOCX, encrypts) before creating an exclusively owned sibling temporary file. It writes and synchronizes that file, closes it, then replaces the destination. Failed preparation or replacement keeps the original bytes; cleanup removes only the save's temporary file, on a best-effort basis. Existing <name>.tmp files, directories and links are untouched. A new document gets the default mode (0666 less the umask). When replacing an existing regular file, the Unix temporary file starts with mode 0600 and then takes the existing file's basic permissions. Serialization and format support are unchanged. Native io::write_file (Print to PDF, file.printPdf; Export Page as PNG, file.exportPng) writes through the same path (#1355). If the folder refuses the temporary file with a permission error (macOS privacy protection, a read-only folder; #2138), an existing destination is never written in place: it stays byte for byte as it was, and the error says to use Save As to another folder or to give WordCraft access to the folder (on macOS, System Settings › Privacy & Security › Files and Folders). Only a destination that doesn't exist yet is created directly (exclusively, so nothing already there is opened); a failed direct write removes it again. Unit tests cover a read-only folder on Unix; the macOS privacy case is not yet confirmed on a Mac. A folder that keeps no Unix modes refuses to set one with "Operation not supported" (a NAS share mounted by GVFS, smb:// in the Linux file manager, refuses every mode change; #3003): the save goes on without copying the mode, since there is none to keep; any other failure to set it still stops the save and keeps the original. Unit tests cover the refusal; not yet confirmed on a real GVFS share. Synthetic CLI cases and engine/tests/it/safe_save.rs cover occupied names, links, blocked replacement, missing directories, Save As session state, password-protected saves and original-file protection on macOS. Unit tests inject preparation errors and interleave two prepared saves. Independent saves use separate files; the last successful replacement wins. This is not document locking or conflict detection. Windows/Linux runtime behavior, ACLs and extended metadata, real disk-full conditions, power loss and network filesystems are not verified by these tests. The containing directory is not explicitly synchronized. Cleanup can fail when storage or permissions change, and process termination can leave a temporary file. No Word observation was needed for this filesystem change; it makes no new format-fidelity claim.

  2. Preserve what we can't render: remaining ink forms and unsupported graphics survive a round trip (keep the parts and the run). Charts, SmartArt and OLE objects do (#292, #319); drawing-level and direct run-level native ink now keep their InkML and optional picture fallback.
  3. Move tracking (w:moveFrom/w:moveTo) read and written (formatting revisions: #41; content controls: #381).
  4. Encrypted .docx opens with a password.

Imported TOC result preservation

Original synthetic TOCs without TOC paragraph styles lose their outer result range on main and #538. Main also flattens a nested page field in a single-paragraph result. Imported TOCs now use the existing range-field markers to retain the actual result boundaries, nested page-reference fields, formatting, links and locks through edited saves.

The public complex-field contract defines begin/separate/end delimiters and permits nested fields. Paragraph styles do not define those boundaries. A complete range is converted to the engine's styled TOC representation only when that writer can reproduce its exact extent; partial or custom-styled ranges stay explicit.

Focused original regressions cover single/multiple paragraphs, partial ranges, adjacent styled text, multiple/simple fields, table cells, section breaks, missing ends and bounded nesting. The existing styled TOC write/read path remains supported. Update Table and Update Fields refresh unlocked top-level body TOC ranges in place through the engine's generator; one undo restores the imported range. Locked, nested and table-cell ranges remain preserved without regeneration. Preservation is separate from field evaluation. Native Word reopening and refresh, full schema validation and company documents remain untested. Synthetic checks do not raise readiness estimates. No Word-derived files are fixtures.

Settings preservation

A save used to regenerate settings.xml from the model alone, so every setting the model doesn't hold was dropped without a warning (on 18 real-world Word documents: compatibility settings in 18 of 18; the privacy options are modelled since #1062). Now the writer merges into the file's original (crates/docx/src/write/settings_merge.rs): the original root and every child the model doesn't own stay byte for byte; owned children follow the model, in CT_Settings order; in w:compat only compatibilityMode is replaced. Kept children that point at a relationship (a mail-merge data source) are dropped. Files WordCraft wrote itself keep nothing extra. Tests: crates/docx/tests/it/settings_merge.rs.

Unmodelled-part preservation

Parts the package or the main document relate to that WordCraft neither models nor writes (web settings, styles-with-effects, add-in task panes, people, the thumbnail, future parts) are carried verbatim with their relationships and content types. The glossary document is carried the same way while its building blocks are as read; once they change it is written from the model. Relationship types the writer produces, and any the document's markup refers to by id, are not (HANDLED_RELS in crates/docx/src/read/embed.rs), so nothing is written twice. app.xml keeps Template, Manager, Company, HyperlinkBase and the link/sharing flags; counts (pages, lines, characters, editing time) and the producing application's version are not carried, and Manager and Company are dropped when the file asks to remove personal information on save. Not yet: unknown elements and attributes inside stories and style or list definitions; a regenerated theme. Tests: crates/docx/tests/it/passthrough.rs, docx::read::embed::tests. The ids the markup refers to are the ones it names in a relationship attribute (r:id, VML's o:relid), taken from the main document the reader has already parsed — not one search per relationship over the main part — so opening a document costs the size of its part and not that size times the number of its relationships: 1024 relationships and a 64 MiB part went from 224 s to 0.2 s (#3411). An id that only appears as text is not a reference: the text names no part, and treating it as one lost the part on save. A producer that left the relationship prefix out is read as it wrote: an unqualified id on an element that carries a relationship names that relationship (xml::is_rel_attr), and the writer keeps the attribute and gives it the id the new package holds the part under; an ordinary id — a VML shape's, a drawing's wp:docPr, a picture's pic:cNvPr — is the element's own and names no part.

Saving legacy Word imports

Word 97–2003 .doc and .dot remain import-only. A user Save without an explicit destination opens the existing Save As flow suggesting DOCX (#2445), including before Close. The original stays unchanged. Cancelling retains the draft, revision and path; a failed write keeps the draft open, and successful DOCX save/reopen retains the edited text. Uppercase extensions follow the same route. Scripts and explicitly supplied legacy destinations still receive an unsupported-format error and never open a dialog. Late Save As answers are rejected before writing if automation has replaced the document.

Original binary fixtures and actual WordApp/Session file I/O cover Save, toolbar dispatch, a Mod+S input event, cancel, failure, retry, close continuation and repeated DOCX saves. The picker service is controlled in these tests; a native Windows picker and broad legacy-document fidelity remain unqualified.

Cached field result formatting

Imported text fields use the first nonempty cached result run's formatting on their paragraph span, including character styles. Empty results retain begin-marker formatting. Synthetic fixtures cover simple and complex fields, default inheritance and repeated saves. Mixed-format results remain represented by one span; field refresh policy is unchanged.

Markdown inline code

Inline code exports each LF, CR or CRLF line ending as one space, following CommonMark code-span normalization. This keeps a following heading, list marker or HTML tag inside the code span, including code in lists and table cells (#3738). Leading and trailing spaces and backtick fences are preserved; fenced code blocks keep their line breaks. Synthetic export/reimport tests cover these cases.

Repeated DOCX style IDs use the last complete definition. The original regression also covers repeated save/reopen, including removal of earlier-only properties.
